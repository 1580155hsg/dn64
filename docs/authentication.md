# 签名与密钥

## 认证模型

DN64 第一版只接受 SSH Ed25519 原生 Git 提交签名。`auth` 格式：

```text
auth:               ssh-ed25519 AAAA...完整公钥...
```

一行一把公钥，不附注释；可登记多把。新 mntner 需要证明持有至少一把新登记密钥。现有对象的修改和删除依据目标主分支原有的 `mnt-by` 和公钥核验，不信任 PR 改写后的身份。

GitHub 用户名、提交作者邮箱和 Verified 标记不代替上述授权。DN64-MNT 是管理员维护者，可授权规则调整和人工恢复；这是一项明确的管理员权限，需要通过 PR 说明理由并保留审计记录。

## 配置

```sh
# 如尚无密钥，生成一把；不要覆盖已有密钥。
ssh-keygen -t ed25519 -f ~/.ssh/dn64_ed25519
git config gpg.format ssh
git config user.signingkey ~/.ssh/dn64_ed25519
git commit -S
```

将 `.pub` 文件里的公钥前两段放入 mntner 的 `auth`。不要提交没有 `.pub` 后缀的私钥文件。使用 ssh-agent 也可以签名，只要签名密钥匹配注册公钥。

## 轮换

1. 保留旧公钥，添加新公钥，用旧密钥签名并提交 PR。
2. 合并后使用新密钥签名，移除不再使用的旧公钥。

这样每一步都由此前已可信的密钥授权。不要在一个普通 PR 中替换掉所有旧公钥；这种操作必须由管理员核实后进行恢复。

## 丢失全部密钥

提出恢复 PR，并联系管理员说明原因。管理员通过原有公开联系方式及其他可信证据核实，随后制作 DN64-MNT 签名的恢复提交。仓库不会仅凭 GitHub 账号或自报邮箱自动恢复。

## 合并签名

PR 需要是当前 main 之上的单个非合并签名提交。仓库仅启用 Create a merge commit，保留原始成员提交及其签名；关闭 GitHub 的 squash/rebase merge。审核后有新推送时，需要重新检查和审核。
